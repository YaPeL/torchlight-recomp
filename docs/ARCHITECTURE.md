# Architecture

```
guest RenderSystem hooks -> Session (command stream) -> Frontend -> OGRE 14 GL backend
                                   |                                ^
                                   +-> F9 capture (.tlcap) -> replay +
                                   +-> LiveFrame (cut at the swap) -> live mode
```

- `src/guest_abi/`: offsets, slots and functions of the guest OGRE 1.7, each with its evidence.
- `src/hooks/`: overrides of guest functions; they translate arguments into commands and call the
  original.
- `src/capture/`: `Session` (shadow state, F9 capture, recording of the live stream),
  `ResourceRegistry` (identity: address + generation) and the guest memory readers.
- `src/commands/`: neutral command format and TLCAP.
- `src/rtss/`: reading of the guest's RTSS programs (constant registers, stages, texgen, Runic's
  skinning).
- `src/frontend/`: the only path to the backend. Used by the replay (frames from a file) and the live
  mode (frames from the guest), through `ContentSource`.
- `src/backend/`: OGRE 14 (GL3+, core profile: the guest's draws with programs generated by the RTSS,
  one per state structure, cached) behind a C API (`backend_api.h`); the Xbox/GL differences live in
  `xbox_to_gl_conventions`. It replaced the backend on OGRE 1.6.1 (tag `v0.1-ogre16`) at parity: PSNR
  equal or better on every capture and the same performance on the recorded session.
- `src/platform/`: everything that depends on the host's window system or video, behind a common
  interface (`platform.h`), one file per platform (today `platform_linux.cpp`: SDL on X11 for the
  game's window, X11 for the keys of the backend's window).
- Files and folders (relocatable build, `platform.h`): nothing is found or written through a path
  compiled in. OGRE's plugins and media are read next to the executable (`ogre/plugins/`,
  `ogre/media/`; the build links them there, the install copies them), the shared libraries through
  the RUNPATH (`$ORIGIN/../lib` installed; the SDK's and OGRE's directories in the build tree) and
  the GPU plugins from the executable's directory (the SDK's rule). What the game writes goes to the
  user's folders, named `TorchlightRecomp` (not `torchlight`, which the PC game's may be;
  `platform/user_folders.h` resolves them and, first thing at startup, renames the old ones: only
  when the new one does not exist and the old one holds this project's files, never replacing or
  deleting, each move logged; tests get every folder below `TORCHLIGHT_TEST_USER_FOLDERS`, set only
  by ctest, so the suite never writes to the real ones): settings and the runtime's
  `torchlight.toml` to `ConfigDir`, the shader cache and the widened layouts to `CacheDir`, the logs
  to `LogDir` (the runtime's log file is chosen in `OnConfigurePaths`, `live::ConfigurePaths`;
  OGRE's is `<log>_ogre.log`), saves to the runtime's data folder (`DataDir`, the runtime's default
  `user_data_root`). The first line of each log names the executable and the build's commit
  (`cmake/build_info.cmake`).
- First start (REL.4, `src/game_setup/`): without `--game_data_root`, the game's files live in
  `platform::GameDataDir()` (`~/.local/share/TorchlightRecomp/game/`; its `import/` is where saves
  to import go). At every start its `default.xex` is checked (size and SHA-256); when it does not
  check out, before the runtime's window exists, a message box asks for the user's Torchlight XBLA
  package or an extracted folder (the system's pickers, SDL3; on the Steam Deck in Desktop Mode). A
  package's header must say LIVE/CON/PIRS, Arcade Title, title `0x58410A7E`; it is extracted with
  the runtime's STFS reader (a folder is copied, never linked) into `game.partial/`, every file
  checked by size and SHA-256 against `game_files_table.inc` (the one supported version, 1.0.140.0;
  `tools/game_files/make_table.py`), then renamed to `game/`; an existing `game/` is moved aside,
  never deleted. A small SDL window shows the progress (ASCII text: SDL's debug font); closing it
  cancels. The texts are English templates with {placeholders} in the code
  (`game_setup/setup_text.h`, `game_files.h`, `install.h`), translated from
  `data/ui/tl_setup_strings.txt` (de, fr, es; written for this project in the register of the game's
  translations) in the host settings' language, else `--user_language`'s, else the system's
  preferred one, else English; `setup_text_test` fails when a text lacks a line in any language. New
  first-start texts go the same way. After the game's files, when `settings.toml` has no
  `achievements` yet, a message box asks which set to earn, Xbox 360 or PC (incomplete), and saves
  the answer (closing it saves Xbox 360); `EnsureAchievementChoice`, before the runtime starts.
  `license_mask` is 1 by default (the full game; decision 1 of
  `docs/release-pipeline.md`), `--license_mask` on the command line wins.
- Release (REL.5-REL.7, `docs/release-pipeline.md`): the SDK (`patches/series`) and OGRE are built
  by `tools/deps/` (Release, `ubuntu:22.04`, clang 21: glibc 2.35 is the floor), keyed by
  `tools/deps/key.sh` and published by CI as `deps-<key>`. `ci.yml` (pull requests, main, by hand)
  builds without the game (`linux-amd64-nogame`), runs the tests and checks a packaged `replay`
  on a `synthetic_capture` in clean `ubuntu:22.04` and `archlinux` containers. `release.yml` (`v*`
  tags, `release` environment) builds the game from the XEX of the private repository (SHA-256
  checked), splits the symbols to the private symbols repository and leaves a draft release.
  `packaging/linux/`: the AppImage (linuxdeploy, appimagetool; our icon; libstdc++ and libgcc_s
  in `usr/lib/compat`, used by `AppRun` only on hosts with an older libstdc++) and its check
  (`check_appimage.sh`: `AppRun` starts an ELF, every library resolves as `AppRun` runs it).
  Checked locally: the game's AppImage built in `ubuntu:22.04` passes in both containers and runs
  the game to the menu. OGRE is linked `--as-needed`: its GL3+ plugin used to ask for `libSM`, `libICE`
  and `libXext` without using them (OGRE links all of `X11_LIBRARIES`); now it needs libX11,
  libXrandr and libEGL only, and the AppImage was checked on Fedora, Ubuntu 22.04 and Arch without
  libSM/libICE on the system.
- Default mode: `--native_live=only` (the native backend is the only renderer, `null` GPU plugin).
  Xenos is still available with `--native_live=off` (or an explicit `--gpu_plugin` without
  `--native_live`), and `parallel` combines it with a second backend window.
- `src/live/`: live mode (phase 1, `--native_live=parallel`): frame queue, content snapshots by
  version, consumer on its own thread with the backend's window.
- Runtime dialogs in only mode (`XamShowKeyboardUI`, `XamShowMessageBoxUI`): without a presenter,
  the SDK would answer them by itself. `live/install.cpp` publishes its own `ImGuiDrawer` whose
  `ImmediateDrawer` is `UiOverlay` (`live/ui_overlay.h`): it records what ImGui emits into UI frames.
  The UI thread draws (the drawer has no locks), the consumer asks for one frame per present and the
  backend draws it last over the whole window (`tl_backend_set_ui_frame`), in ImGui's logical space
  scaled to the window's pixels: the same factor the SDK uses for the mouse, so the click lands where
  it is drawn at any display scale (verified at 150 % on Wayland and on X11, game image included).
  With dialogs open the guest's input is cut (`InputSystem::SetActiveCallback`, as `ReXApp` does with
  its overlays; it stays cut until the pad is released, so the A that confirms does not reach the
  game) and the pad, read by the platform, navigates ImGui (`live/ui_gamepad.h`). With Xenos the
  dialogs are the SDK's; the guest's input is cut while a XAM one is open (`xeXamIsUIActive`),
  without the cut until the pad is released. Outside `commands/` and the captures. Full design:
  `docs/text-input-research.md` (branch `research/installer-input-saves`).
- `src/settings/`: the host's settings, what the game does not know about (render system, GPU,
  internal resolution, FPS cap, vsync, aspect ratio, achievement set), in `settings.toml` in the platform's
  configuration folder (`platform::ConfigDir`; Linux: `$XDG_CONFIG_HOME/TorchlightRecomp/` or
  `~/.config/TorchlightRecomp/`). The
  game's settings stay in its save (`SAVE:\local_settings.txt` and `settings.txt`, UTF-16BE, read
  when the save device is mounted). They are read in `PreCreate`, before GL is loaded. What each
  machine offers comes in as `Capabilities` (filled by the platform and the backend) and the menu
  shows only that, with what needs a restart marked. In only mode they are applied like this:
  - vsync: the backend window's;
  - FPS cap: the null GPU's vblank rate (the game advances by real time); today the runtime's
    `vsync` cvar gives 60 or uncapped;
  - resolution: the backend's internal scale (`tl_backend_set_render_scale`, `RenderScale` in
    `backend.cpp`). The main target and the output are created at N times the guest size; the
    guest's render targets are not, because it samples them as textures (shadows and lights with
    clamp: larger ones change their texels and stretch the shadows at the edges). Everything the
    guest gives in pixels stays in its units: viewports as a fraction of the guest size, D3D's half
    pixel in guest pixels and readbacks at the guest size. The scale is the one at which the guest's
    frame fits in the chosen resolution (by default, the window's).
- `src/guest_abi/game_ui.h`: the game's UI (Runic on CEGUI 0.6): the menus (`CDropdownMenu`), their
  `.uilayout` layouts (CEGUI XML), the `onClick` commands and pad navigation.
- `src/game_menu/`: the host's settings inside the game's settings menu (only mode), as a "Video"
  column to the right of its rows, in its style. It is all the game's own UI:
  - the layout is ours (`data/ui/tl_video_settings.uilayout`, copied next to the executable) and only
    references widget types, fonts and imagesets from the pak; the guest sees it through a VFS device
    (`tlhost:`) added as an OGRE `FileSystem` location after `resources.cfg`;
  - after the settings menu's init it is loaded, scaled the way the game scales its layouts and
    attached to its container; the pad order is built on the first opening, so the rows are
    navigable. Every window has its own name (`tl_video/...`): the guest's unique name generator
    produces names that clash;
  - a hook on the menu's navigation handler (by identity of the menu and of our rows): left/right
    change the value, A the vsync; the rest follows the game. "Reset Defaults" also resets the
    column;
  - changes apply immediately (scale and vsync through a request to the backend thread, the cap
    through `SetGuestVblankRate`) and `settings.toml` is saved; language, renderer and GPU show the
    restart notice. The model (`video_menu_model`) does not depend on the guest and has tests;
  - the labels and the word values are translated with `data/ui/tl_video_strings.txt` (de, fr, es;
    written by us: the game does not have those texts) into the language the runtime reports;
  - the GPU (Linux only for now) is chosen before GL is loaded: the driver variables
    `platform::GpuEnvironment` returns for each GPU (`__NV_PRIME_RENDER_OFFLOAD` for NVIDIA's
    proprietary driver, `DRI_PRIME` for Mesa), applied in `PreCreate`; if any graphics library is
    already loaded the option is disabled;
  - every call into the guest is from a hook, on the game thread (`GuestCall`: its own frame on the
    guest stack, registers restored); CEGUI is not thread-safe. `CGameUI` builds its menus once per
    process and the column lives and dies with the settings menu.
- Difference with the Xbox 360, the save indicator (`game_menu/save_indicator.cpp`): closing it,
  the game sleeps on its render thread until it has been up for 1 s, or 3 s once the save took
  over 1 s (`CGameUI::ShowSaveIndicator`, `sub_82344EE0`, see `guest_abi/game_ui.h`). It is the
  console's certification minimum, not protection of the data: the save is written before the
  indicator closes (in the logs the save's last file operation comes about 1 s before the frame
  ends). On the host the save takes milliseconds, so every autosave and zone change froze the game
  for about a second. The PC version has no such wait (its only `Sleep` call is the C runtime's
  startup). That `Sleep` is skipped; the indicator opens and closes as before. The full autosave
  notice, shown once per session, keeps its 5 s minimum: the player has to read it.
- Screens other than 16:9 and 4:3 (ultrawide 21:9 and 32:9, and 16:10; TLR-006), only mode. With
  Xenos the game keeps its 16:9. Validated with captures at 21:9 (1680x720), 32:9 (2560x720) and
  16:10 (1280x800):
  - Aspect setting (`aspect` in `settings.toml`, a row of the Video column, after a restart):
    automatic (the default: the game display's) or 4:3, 16:10, 16:9, 21:9, 32:9; the menu offers
    only those no wider than the display. At the start of `OnPostSetup` (window open, guest not run
    yet) `live::ApplyAspect` sets the SDK's `video_mode_width/height` cvars, which the guest reads
    as its video mode, to `hooks::VideoModeForAspect`: 720 lines at that aspect, kept within 4:3 to
    32:9. For 4:3 (and anything narrower, such as a 5:4 display) it reports 956x720: the SDK calls a
    mode widescreen when `width * 3 >= height * 4`, so an exact 4:3 would make the game pick its
    16:9 mode. Wider than 32:9 (several screens) gives 32:9. A `--video_mode_width/height` on the
    command line wins.
  - Frame (`hooks/video_mode.h`, `FrameSizeForVideoMode`): 16:10 gives 1280x800; any other aspect
    keeps 720 lines and a width in multiples of 80 (the guest D3D sizes surfaces in EDRAM tiles), at
    most 2560 (32:9). The guest's width and height come from a fixed table (1280x720 or 960x720),
    and its render system picks and parses the mode by its name ("1280 x 720 @ 32-bit colour"). So,
    before the guest runs, the name literal is rewritten to the new size (same length) and the
    descriptors of the 16:9 mode are retargeted when they reach the mode list and the driver record
    (`hooks/video_mode_hooks.cpp`). The back buffer, the viewports and the camera's aspect follow.
    The 3D view widens with the frame (the camera's vertical FOV is fixed).
  - EDRAM aliasing: the guest D3D's EDRAM bookkeeping (10 MB, 2048 tiles) has no room for a wider
    back buffer next to the game's render targets, and a refused render target is a breakpoint trap.
    A render target refused for lack of EDRAM is created again aliased at EDRAM base 0
    (`D3DSURFACE_PARAMETERS`, which does not allocate). Its release then frees no EDRAM, because the
    owned bit is not set. With the null GPU there is no EDRAM, and the GPU commands that would use
    the base are discarded. That is why this is only mode.
  - Layout bands (`game_menu/wide_layout.h`, `WidenBands`): menus and loading screens build their
    top and bottom bands from a centred image of fixed width plus two end pieces anchored to the
    screen's edges. At 1280 they overlap into one band; wider, they leave gaps. The end pieces are
    re-anchored to the edges of a centred 16:9 area (`{0.5, ±offset}`), keeping their overlap. The
    rule is structural, with nothing matched by name. The pak's layouts that have bands are written,
    widened, to the platform's cache folder (`platform::CacheDir("layouts")`; Linux:
    `~/.cache/TorchlightRecomp/layouts/`). That folder is mounted as `tlwide:` and added as a
    resource location in the default group, after `resources.cfg`, so the game finds those layouts
    there first (as the language pack's fonts). They are regenerated on every start with a wider
    frame.
  - Front end scene clip (`SceneClip16x9` in `backend.cpp`): in the main menu and character creation
    the game's 3D scene is built for 16:9, so a wider frame shows its edges. The hook on
    `CreateViewports` (`sub_8220A470`, read only) keeps the scene viewport. While the frame is wider
    than 16:9 and the game is not in a level (`InLevel`: the `CGameUI` chain to the level flag, see
    `guest_abi/guest_functions.h`), each swap sends `SetSceneClip` with that viewport (0 otherwise;
    TLCAP 1.6). The backend draws that viewport's draws only inside the main target's centred 16:9
    strip (scissor), and its clears paint black outside the strip. The UI and in-level scenes keep
    the full width. At 16:10 (taller than 16:9) the clip never applies.
- `tools/replay`, `tools/capture_dump`: offscreen replay with a metric against the reference, and a
  readable dump of captures.

## Pending for phase 2

The performance of phase 1 (Xenos and OGRE at once) is not optimized: it is a validation tool. In
phase 2 we need to measure:

- Lock contention in the producer (`Session`: resource registry, content versions, snapshot store).
  In `--native_live=parallel_nodraw` the producer reached 33-107 ms per frame in heavy scenes,
  against 1-7 ms in other runs of the same scene.
- Cost per producer hook (today the summary only separates constants, other commands, snapshots,
  version marking and frame cut).
- Thermal throttling of the test machine during long runs.

## Known pending items

- "Broken" autosave widget the second time (closed, not a bug): the game shows the full autosave
  notice ("This game has an autosave feature...") only on the first save; after that it shows only
  the icon. Xenos does the same. Found with the session recording (`--live_record` +
  `replay --session`), which replays frame by frame what the backend consumed. The choice is made by
  `sub_82363E40` (`CGameSaveMenuXenon`): full dialog only if the global 0x8355A264 is 0. That global
  is written only by `sub_82195AA8`, the state machine that polls the asynchronous storage operations
  (`XNotifyGetNext` + XOVERLAPPED): it becomes 1 when there is a chosen device (the SDK's headless
  selector returns device 1) and goes back to 0 if it is lost. It is not saved to disk: the notice
  shows once per session. The `ResolvePath(SAVE:\)` calls in the log are optional reads
  (`local_settings.txt`, `resourceconfig.dat`) while the `SAVE` container is not mounted (the game
  mounts it only around each save); the saves are written fine to
  `~/.local/share/TorchlightRecomp/<xuid>/58410A7E/00000001/torchlight.sav/`.
- The game's options persist (validated 2026-10-06 on a copy): they are written to the save's
  `settings.txt` and `local_settings.txt` inside the game's mount bracket and are back after a
  restart; the 28 `ResolvePath(SAVE:\)` errors per run (the options and `resourceconfig.dat`
  readers at startup and at the main menu, before anything is mounted) lose nothing. Not checked:
  whether the console's XAM has the save mountable at startup; it changes nothing observable.
- Guest exceptions, not implemented by the SDK and left as they are (nothing observable breaks):
  - `RtlUnwind` is a stub (`[STUB] RtlUnwind called`, once per run at the main menu). The call is
    almost certainly the CRT's `_wfopen` (`sub_8285EAC8`) given an empty name (no `SAVE:` yet):
    it returns NULL as it should, but the `__finally` that unlocks the CRT stream it reserved is
    skipped, so one `FILE` lock stays held by the game's thread. Recursive, so that thread is not
    affected; another guest thread using the same CRT stream would block (never seen). A fix: an
    SDK `RtlUnwind` for local unwinds (the function's `.pdata` entry, its `__C_specific_handler`
    scope table, the `__finally` handlers covering the call).
  - C++ `throw` (`_CxxThrowException` `sub_82865D90`, 33 call sites, OGRE and the C++ library):
    the SDK's `RtlRaiseException` only calls `debug::Break` (SIGTRAP: the first one survives on
    Linux, a second one or any on Windows ends the process). Never seen, so the game does not throw
    in normal play. Implementing it means a code generator change (host exceptions, catch
    continuation labels, guest unwind maps): only if a real case shows up.
  - `setjmp`/`longjmp` (`0x82864230`, 13 callers; `0x828636E0`, 25 callers; image libraries'
    error paths): the manifest does not declare them (`setjmp_address`, `longjmp_address`, which
    the SDK's code generator supports), so a guest `longjmp` returns to its caller instead of
    jumping. Only reached on a decoding error; never seen.
- Automatic selection of the first character when entering "load character", the story screen
  skipped on entering the mine (closed): the SDK's SDL driver repeated a key that had been released
  while the game was not reading keystrokes (a loading screen), before reporting its up. Fixed by
  SDK patch 16 (`patches/README.md`); with Xenos it happened the same way.
- Guest memory left in `/dev/shm` by runs that end by a signal (closed): SDK patch 15 unlinks the
  shared memory right after creating it. The cleanup loop in docs/BUILDING.md is still useful for files left
  by runs with an SDK without the patch. Pending: the upstream report.
- Full-screen images on screens wider than 16:9 (TLR-006.5, after the beta): loading and story
  screens show their image pillarboxed with continuous bands, which looks right. To review: on the
  story screen at 32:9 (in level, so without the scene clip) a few rows of the level's scene show at
  the top right, past the end of the top band (x ~1880-2075 of 2560).
- Mesa against NVIDIA on the 2D screens (loading screens, menus): the same replay gives 59.3 dB
  against Xenos with Mesa (Intel UHD 630) and 69.8-69.9 dB with NVIDIA (GTX 1050 Ti on Linux, RTX
  5080 on Windows): at most 5 levels per channel from Xenos with Mesa, 2 with NVIDIA (capture v18).
  The 3D scenes differ by under 1 dB. Not a build difference. Relevant for the Steam Deck, which
  uses Mesa: compare its captures against a Mesa reference, not an NVIDIA one.
- Import of PC saves from the "load character" menu (`game_menu/save_import_menu.cpp`,
  `docs/saves-research.md` section 4d): validated in the game except two paths only the tests cover
  (`src/save_import/import_plan_test.cpp`, `import_message_test.cpp`): the hardcore shared stash
  (`sharedstashh.bin`, imported and replaced like `sharedstash.bin`) and the "Do not ask again"
  button (the files become `.skipped`). Pending: a run with a test `import/` folder and
  `--user_data_root` on a copy of the saves.
- The guest's GPU wait (`hooks/gpu_wait_hooks.cpp`): sleeping 200 us on every wait step took the
  guest's main thread from 100 % to 23.6 % of a core on Linux in the menu (the whole process from
  154 % to 67 %), with the same frame times, latency and loads; 37 % on Windows, where it changed
  little. With the hook, a profile of the main thread (gdb, 80 samples) finds it asleep in that wait
  50 times and in the game's own scene and render code the other 30: no other busy wait. A first
  measurement had shown 68 %: that run had MangoHud's library loaded, which costs CPU even without
  drawing.
- After the beta: with the GPU wait hook the main thread wakes about 2700 times per second (200 us
  sleeps while the guest waits for the GPU). On the Steam Deck on battery that may cost power; to
  measure there before changing anything (a longer sleep, or waking on the GPU's progress instead).
- Counting guest interrupts: a hook on its ISR (0x82775610) hung Xenos mode at startup (not only
  mode); it was removed without understanding the cause.
- MangoHud in only mode: Debian/Ubuntu's uses the system spdlog (1.15, dynamic) and `librexruntime`
  exports its whole spdlog 1.17 (template instantiations included). On the first `eglSwapBuffers`
  MangoHud creates its logger and `ansicolor_sink::set_formatter` resolves against the runtime's
  copy: `free(): invalid pointer` (confirmed with the stack). A MangoHud built with its internal
  spdlog is used (docs/BUILDING.md). For the Steam Deck: Game Mode's performance overlay is `mangoapp` inside
  gamescope, a separate process that is not injected into the game; verify it when we test there
  (`gamescope --mangoapp` also works on the desktop). Possible upstream report to the SDK: that
  `librexruntime` not export spdlog or fmt (today its public logging headers expose spdlog types, so
  it is not a small change).
- Drawing at the window's resolution instead of the guest's (720p) and scaling: its own task.
- "No view space" in live mode: happens only during loading screens (about 50 draws per frame); in
  the steady game and in the replay of captures (also with `--live_content` and `--via_live`) it does
  not appear. Minor; not analyzed.
- Reading a render target mid-frame from the CPU (`convertToImage` and the like) leaves the GL state
  different from what OGRE thinks it has (texture and framebuffer bindings), and the following draws
  come out wrong. It happened twice with diagnostic tools (the last one, the dump of the waves draw
  of v14/031917, which made it look like the guest's fog did not work). Reads only after
  `tl_backend_end`, as `tl_backend_read_rgba` and `tl_backend_read_target_rgba` do. If the guest read
  an RT from the CPU live (`render_target_blits_to_memory` in the summary) it would have to be solved
  in the backend. It still happens on GL3+ (same test, same result).
- Black lines around the autosave icon (closed): it was sampling off by half a pixel; with
  `D3DPixelCentresToGl` they are not visible, same as in Xenos.
- Skinning without lighting and the normal used for texgen (closed): the RTSS `HardwareSkinning`
  only skins the normal when the pass has lighting. Among the 67 known programs (inventory
  `out/programs/all` plus those of the 20 captures) there are 13 vertex programs with skinning: the 2
  without lighting do not use texgen, and those using an env map (normal or sphere) have lighting.
  Not exhaustive: a new program with that case would draw the texgen with the unskinned normal.

## Cross-platform stage (Linux, Windows, macOS, Steam Deck)

- OGRE build described inside the project (pinned version, exact CMake configuration), so it is
  reproducible on the four platforms; today it is built by hand in `~/ogre14-install`.
- Optimize the backend: the town went from 20-35 to 46-60 fps (program analysis cached in the
  frontend; the producer does not re-emit unchanged state: ~8800 -> ~2000 commands per frame). In the
  heaviest areas the consumer still takes 18-19 ms per frame (~400 `bindGpuProgramParameters` per
  frame). The Steam Deck's CPU is quite a bit more modest. Reference session to measure:
  `out/sessions/town2.tlses` (`commands consumed` summary in `replay --session`).
- Intel UHD 630 (session `out/sessions/intel.tlses`): the bottleneck is the CPU. GPU, measured with
  i915's `drm-engine-render` counter in `/proc/<pid>/fdinfo` during the replay: ~2.9 ms per frame in
  the heavy areas (~285 draws), 2.7 ms on average; the present waits ~0.6 ms. Backend CPU: removed
  the quadratic `Finish` of the live content, and the creation and destruction of one GPU buffer per
  version of each dynamic buffer and of one VAO per draw (full session 88-90 s -> 78-80 s).
  `--live_record` costs ~9 ms per frame on the backend thread: do not record when measuring. MangoHud
  does not read this Intel's GPU load (`gpu_load` 0).
- Live run on the Intel with the performance governor (heavy areas of the town and the mine): the
  backend is no longer the bottleneck (~4.8 ms of work per frame, no drops); the limit is the game
  thread, which with our producer hooks (~5 ms) goes from 17 to 21 ms. Without the hooks, the game
  alone uses 12-16 ms, and at the heaviest peak ~16 ms: on the Steam Deck, with a CPU 10-20 % slower,
  those peaks will go past 16.7 ms even if our cost were zero.
- Producer optimization (Intel, performance, same load of ~230-245 draws per frame): from 4.0-4.3 to
  3.2-3.6 ms per frame (constants 0.7 -> 0.4, state hooks and draws 2.8-3.05 -> 2.4-2.7, buffer
  snapshots 0.47 -> 0.3), from 16.4-17.8 to 14.4-14.5 us per draw; the guest frame stayed at a solid
  60 fps in the areas played, with no drops. Changes: the producer's cost is measured in 1 of every 8
  frames (the timers cost ~0.7 ms per frame), no command copies in live mode, interned auto-constant
  names, early exit on raw arguments in the state hooks and a per-buffer snapshot cache. The early
  exit yielded ~0.4 ms and not the ~2 ms estimated: with ~11000 calls per frame the fixed cost of
  each hook dominates.
- Producer pending items, to pick up if the peak is a problem on the Steam Deck:
  - Cache what `setVertexDeclaration` and `setVertexBufferBinding` read from the guest by pointer,
    with a version bumped by the hook that modifies the declaration: ~0.3-0.5 ms per frame (today
    0.54 and 0.32 ms in ~305 draws).
  - Measure the fixed cost per hook (slot counter, jump, comparison and guest memory read) over the
    ~11000 calls per frame, to see whether it can be lowered; it cannot be deduced from the code.
- Shader compilation: the program's structure does not depend on the view space or the alpha test
  function, so almost all are created during loads (in the middle of play about 5 new pairs remain).
  First use of a program (RTSS generation + compilation), town2: with the driver's shader cache warm,
  median 1.3 ms and max 5 ms; cold, median 17 ms and max 80-115 ms. The hitch can only appear on the
  first run (or after a driver update). OGRE's microcode cache and a local list of pairs were
  discarded: both are empty exactly on that run and afterwards the driver's cache already covers the
  case. The decision to have no cache of our own relies on that driver cache, guaranteed on Linux
  with NVIDIA and Mesa (Steam Deck included) and on Windows. Pending when testing on macOS: if
  Apple's GL does not cache well, evaluate OGRE's microcode cache there, first solving the rejected
  binary problem.
- OGRE 14.6 bug (possible upstream report), confirmed by reading the code and with a test:
  `GpuProgramManager::addMicrocodeToCache` (`OgreGpuProgramManager.cpp:314-328`) marks the cache as
  modified only on insertion. When the driver rejects a binary loaded from the cache, GL3+ recompiles
  from source and replaces the entry without marking it, so `saveMicrocodeCache` does not write and
  the rejected binary stays in the file forever (every run recompiles that program again silently).
- Platform code isolated (CLAUDE.md rule): everything from `live/install.cpp` and the backend is in
  `src/platform/`. Wayland and X11: the platform uses the driver SDL picked and gives the backend the
  neutral window (`tl_native_window`). On X11 OGRE creates a child window; on Wayland (no child
  windows) it draws directly on SDL's `wl_surface`, with the GL3+ plugin built with
  `OGRE_USE_WAYLAND` (`lib/OGRE/wayland/`). On Windows there is no child window either: OGRE's
  Win32 GL window takes the `parentWindowHandle` as its own and draws on SDL's `HWND` with WGL
  (`docs/windows-port.md`). The replay (top-level windows) stays on X11 on Linux. The game runs
  only in fullscreen (the SDK's `fullscreen` cvar, on by default); windowed mode is out of scope. If
  the surface stops being visible (alt-tab, another desktop) the compositor sends no frame callbacks
  and, with vsync, the swap on Wayland blocks until it comes back (on XWayland it drops to 1 per
  second): the backend pauses, the guest does not. Closing the game from outside without returning to
  it would hang the shutdown; accepted as an edge case. Known risk: OGRE calls
  `wl_display_dispatch_pending` from the backend thread when creating the window and when resizing
  it, while SDL dispatches on the main one.

## Pending after the merge

- Move to OGRE 14's RTSS, in progress. Done: the guest's draws use RTSS programs on GL3+
  (`ApplyProgram`; our own SubRenderState, `GuestTexgen`, computes the coordinates the RTSS does not
  compute like the guest: view normal on 2D textures and the reflection of
  `FFP_GenerateTexCoord_EnvMap_Reflect`, with the unnormalized normal, see
  `ReflectionMatrixForHost`). GPU skinning with the RTSS's linear `HardwareSkinning` (the guest's
  bones as object space bones; `BlendLanesForHost` adapts Runic's index and weight lanes). The alpha
  test is part of the program (`GuestAlphaTest`) and the fullscreen passes (gamma, presentation) use
  their own programs. The lighting is the guest's (`GuestLighting`, the formula of Runic's
  `FFP_Light_Directional_Diffuse` without clamping); it replaced the RTSS's, which saturates the
  color (`FFP_SATURATE`) and forced dividing the light and compensating in the stage. A custom
  lighting SubRenderState has to link the vertex color to the fragment program itself (the RTSS does
  it only for its `FFPLighting`, `fixupFFPLighting`). Not yet tested in the game: the live mode's
  child window on GL3+. The fog is the guest's (`GuestPixelFog`): the RTSS's also blends the alpha
  with the fog's and Runic's FFPLib keeps it (it showed in the waves draw of v14/031917).

## Future improvements

- Mods (outside the first version). The 360 keeps the structure of the PC mod system but not the
  loader: the mod manager (global `0x83559518`), the `mod.dat` reader (NAME, AUTHOR, DESCRIPTION;
  `sub_823A9EA0`), the lookups by name when starting a game (`sub_82256AA0`, `sub_8225F590`) and the
  `CharacterModsWarning` notice; the only function that adds mods to the list (`sub_82268300`) has no
  callers and there is no folder search (PC: `Runic Games\Torchlight\Mods`, `mods.dat`,
  `GetModNames`). Reviving them means rebuilding the loader and the PC data merge.
- Languages, second stage: Chinese and Japanese. There are community patches for PC (the Japanese
  one only replaces the font, which confirms the game's CEGUI draws CJK from a TTF); the Chinese
  patches touch DLLs, and before promising them we need to see why (probably line breaking without
  spaces).
- Languages out of scope: Arabic. It is written right to left with letters that change shape
  depending on their neighbors; the game's CEGUI 0.6 does neither, and the texts the game composes at
  runtime (items with affixes, numbers) would stay in left-to-right order.
- FPS limit: the PC version runs uncapped (120 fps). The savefile has a parameter that controls the
  fps and also keeps the PC settings (resolution, shadows, AA). Unlock the limit and restore that
  menu.
